## 零、一句话结论

现有后台是一个**能用的通用后台骨架**（登录、账号、角色、日志、配置齐备），
但**机匠学院的业务域是空的**——专业、课程、章节、学习路线、3D 案例、AI 知识库、
学员用户、题库、会员，九个模块里有七个没有任何数据表和页面。

所以这不是"查漏补缺"，是"在骨架上长出业务"。好消息是骨架质量够用，
不需要推倒重做。

## 三、九个模块的差距分析

### 3.1 数据仪表盘（需要完善）

现有看板回答的是"后台谁在登录"，产品要回答的是"学员在学什么、内容够不够"。
需要补的指标：

- 用户统计：新增/活跃/留存、按专业分布、按水平分布
- 学习统计：课程学习人数、章节完成率、人均学习时长、断点分布
- 内容统计：专业/课程/章节/案例/题目数量，各状态数量（草稿/待审/已发布）

**这些指标全部依赖后面 4 个模块先建表**，所以看板改造必须排在内容域之后。

### 3.2 课程内容管理（未开发）

文档要求 5 个页面，本质是 **3 层结构 + 1 套状态机**：

```
专业 major
└── 课程 course（可被多条路线引用）
    └── 章节 chapter（支持两级：章 / 知识点）
```

三个设计要点：

1. **课程不隶属路线**。路线通过关联表引用课程，否则一门课出现在两条路线里就要录两遍，
   后续维护必然分叉。
2. **状态机统一**：`draft → pending → published → offline`，全站内容共用一套，
   不要每个模块自定义。
3. **软删除**：课程被删但学员有学习记录时，硬删会造成脏数据。所有内容表加 `deletedAt`。

### 3.3 学习路线管理（已完成）

```
路线 path ── 阶段 stage ── 关联项 item(courseId, sort, required, unlockRule)
```

难点不在增删改查，在**顺序与前置条件**：文档要求"拖动排序 + 前置课程/解锁条件"。
建议第一版只做 `sort` 排序 + `required` 必学标记，解锁条件留字段但不做规则引擎，
等小程序端真需要时再补。避免为一个用不上的功能写复杂逻辑。

### 3.4 3D 案例管理（未开发，工作量最大）

这是产品的差异化核心，也是**唯一不能边做边改数据结构的模块**。
文档列了 9 个页面，本质是四个实体的三方关联：

```
案例 case3d
├── 固定程序 program（含版本）
│   └── 程序行 line（行号、代码、含义、动作、注意、时间区间）
└── 动画片段 clip（资源地址、起止时间）
        ↑
    line.timeStart / timeEnd 指向 clip 的时间轴
```

关键判断：**把"动画片段"和"程序行"解耦，靠时间轴关联**，而不是让一条程序行绑定一个片段。
因为实际制作时，一条 G 代码可能对应多个动画动作（如 G74 的每个啄钻循环），
一对一绑定会立刻不够用。

三个必须先定的字段：

| 字段 | 为什么关键 |
| --- | --- |
| `system` / `machine` / `scope` | 文档明确要求标注系统与机型。FANUC 0i 和 31i 的 G74 参数含义不同，不标注就是错误教学 |
| `program.version` | 程序会被修订，学员看的是哪一版必须可追溯 |
| `access`（free/member） | 会员权益要在服务端判定，字段必须在案例表上，不能靠前端隐藏 |

另外，**案例预览播放器（Three.js + 时间轴）是一个独立前端工程**，
不建议塞进当前 Vue 后台的构建里，建议独立页面 + 独立资源目录。

### 3.5 AI 知识库管理（未开发）

```
资料 doc（来源/作者/版权/专业/机型/系统/版本）
  └── 分块 chunk（内容、序号、标签、是否可检索）
        └── 审核状态
```

要点：

1. **版权字段是一等公民**，不是备注。文档明确禁止把未授权资料导入对外知识库，
   所以 `copyright`、`license`、`allowPublic` 必须是独立字段并可筛选。
2. **解析是异步的**。上传后状态应为 `uploaded → parsing → parsed / failed`，
   后台要能看到失败原因，否则运营会反复重传同一份文件。
3. **检索测试页**是验收 AI 接入的唯一手段，优先级应高于"分块详情页"。

### 3.6 用户管理（未开发，且最容易被搞混）

现有 `admin_user` 是**后台管理员**，与小程序学员完全是两类主体：

| | 后台管理员 | 小程序学员 |
| --- | --- | --- |
| 登录方式 | 账号 + 密码 | 微信 openid 静默登录 |
| 归属 | 角色权限 | 专业、水平、学习目标 |
| 数据量级 | 个位数 | 万级 |

**必须新建 `mp_user` 表，不要往 `admin_user` 里加字段**。混表的后果是权限模型被污染，
每查一次后台账号都要附加 `where type=admin` 条件。

文档要求 4 个页面（列表/详情/学习记录/会员记录），其中"学习记录"依赖课程模块，
应排在课程之后。

### 3.7 题库与训练（未开发，P1）

题型：单选、多选、判断、填空、实操。建议 `options` 用 JSON 字段而不是拆表，
因为题型之间字段差异大，拆表会产生大量空列。

### 3.8 会员与权益（未开发，P1）

文档的核心要求是"**把会员身份和资源访问权限分开**"：

```
套餐 plan（价格、期限）
权益 entitlement（planId + resourceType + resourceId）
会员 member（userId + planId + 有效期）
```

判定函数应该只有一个：`CanAccess(userId, resourceType, resourceId) bool`，
所有接口调它。**不允许在每个业务接口里写 `if !isMember`。**

### 3.9 系统设置（基本完成）

已有管理员、角色权限、操作日志、系统参数。缺 **AI 接口配置**（模型、超时、限流、
Key 掩码显示）。这是 P0-EX 的小任务，半天可完成。

## 四、三个必须先解决的架构问题

不是缺页面，是缺决策。这三件事定错了，后面返工代价很大。

### 4.1 技术栈与文档不一致（需要你确认）

| 项 | 文档建议 | 实际 | 建议 |
| --- | --- | --- | --- |
| 后端框架 | Go + Gin | 标准库 `net/http` + 自研路由表 | **保持现状**。现有路由表已实现鉴权、权限码、操作日志三合一，换 Gin 要重写这套并重测，收益只是中间件生态，当前用不上 |
| 数据库 | PostgreSQL | MySQL 5.7（腾讯云 CynosDB） | **保持 MySQL**。已在云托管内网配通，迁 PG 需要重做连接与部署 |
| 管理后台 | 沿用现有 | Vue3 + Vite + Element Plus | 符合，继续 |
| 小程序 | 微信原生 | 未开始 | 一致 |

如果你的 Gin / PostgreSQL 是硬约束（比如团队统一规范），**现在说，趁业务表还是零**。
等 10 张业务表建完再迁，成本翻倍。

### 4.2 权限码要从 14 个扩到 40+

业务模块加进来后，模块数是现在的近 3 倍。当前 `permissionCatalog` 是手写数组，
极易漏项——漏了的表现是"运营能进页面但接口 403"，很难排查。

建议：权限码由模块注册表自动生成，每个模块声明 `{code, name, readonly}`，
菜单、路由、权限目录、角色勾选页全部读同一份配置。

### 4.3 文件资源没有落点

文档有 5 处涉及上传（课程封面、附件、3D 动画、知识库资料、头像）。
现在完全没有存储方案。建议先用**对象存储 + 服务端签名直传**，
数据库只存 key 不存 URL，避免换存储域名时全库改数据。

## 五、任务拆解（可直接派给 Bot）

每个任务都给页面、接口、表、验收，按下述顺序做，依赖关系不会打架。

### P0-1 内容域地基（专业 / 课程 / 章节）

**表**
```
major   : id, code, name, icon, summary, sort, status
course  : id, majorId, name, cover, difficulty(1-3), summary, hours,
          status, sort, deletedAt, createdAt, updatedAt
chapter : id, courseId, parentId, title, summary, duration, sort, status, deletedAt
```

**页面**：专业列表（表格+拖拽排序）、课程列表（按专业筛选）、课程编辑（抽屉/独立页）、
章节树（左树右表单）

**接口**：`majors` / `courses` / `chapters` 各 5 个（列表、详情、保存、删除、排序）

**验收**
- 新建专业 → 建课程 → 建两级章节，刷新不丢数据
- 删除有章节的课程时二次确认，且为软删除
- 课程状态可切到 `published`，未发布课程不出现在小程序接口

### P0-2 学习路线（已完成）

**表**：`learning_path`、`path_stage`、`path_item(courseId, sort, required, unlockRule)`

**验收**：一门课可被两条路线引用；调整阶段顺序后小程序端顺序同步；
路线预览页能按学员视角渲染出三阶段树。

**实际交付**：`/paths` 列表页 + `/paths/:id` 编排页，14 个接口；
发布前校验「至少一个阶段且每个阶段都有课程」；删除阶段级联清除课程引用；
课程被路线引用时拒绝删除并列出引用它的路线名；
解锁条件第一版只存文案，不做规则引擎（与审查建议一致）。
